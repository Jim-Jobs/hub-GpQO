# ChatBI / Data Agent — 项目设计

> 本文档定义项目的「为什么做」和「做成什么样」，是功能设计与技术设计的上游依据。

## 1. 项目背景

传统 BI（Business Intelligence）要求使用者具备 SQL 能力、数据建模能力和报表工具操作能力，数据消费的门槛高、链路长：

```
业务提问 → 提需求给数据分析师 → 写 SQL / 拖拽报表 → 出图 → 反馈业务
```

这个链路存在三个痛点：

1. **门槛高**：业务人员不会 SQL，无法自助取数。
2. **响应慢**：依赖数据团队排期，一个问题往往要等几小时到几天。
3. **洞察浅**：报表是静态的，无法针对「为什么」进行连续的探索式追问。

大模型（LLM）的语义理解与代码生成能力，让「用自然语言直接和数据对话」成为可能。ChatBI / Data Agent 就是把 LLM 作为一个**会写 SQL、会做分析、会画图表的数据分析师**，接在业务和数据之间。

## 2. 项目定位

构建一个 **对话式数据分析智能体（Data Agent）**：用户用自然语言提出业务问题，系统自动完成

```
理解问题 → 定位数据 → 生成查询 → 执行取数 → 分析结果 → 生成结论与图表 → 支持多轮追问
```

本项目定位为一份**完整的设计方案（蓝图）**：不追求一次性实现全部功能，而是清晰定义能力地图、系统边界与演进路线，使后续可以按阶段增量落地。

## 3. 核心设计取向

在需求澄清中确认了本项目的五个关键取向，它们贯穿后续所有设计：

| 维度 | 取向 | 含义 |
|---|---|---|
| 数据源 | **多数据源抽象层** | 不绑定单一数据库，通过统一接口接入 SQLite / MySQL / PostgreSQL / REST API 等多种数据源 |
| 核心链路 | **深度研究式分析** | 不止「一问一答取个数」，而是能自主拆解复杂问题、多步查询、交叉验证、汇总成洞察结论 |
| 交互形态 | **Web 聊天界面** | 浏览器对话式产品，呈现文字结论 + 数据表格 + 图表 + 查询溯源 |
| 智能程度 | **RAG 增强语义层** | 将表结构、字段业务含义、术语字典、历史问答向量化，提升 Text-to-SQL 准确率并降低幻觉 |
| 大模型 | **模型无关 / 可切换** | 通过适配层封装 LLM 调用，可切换 DeepSeek / GPT / Claude / 本地模型，不锁定厂商 |

## 4. 项目目标

### 4.1 业务目标

- 让**不懂 SQL 的业务人员**能通过自然语言完成 80% 的日常取数与简单分析。
- 将常见数据问题的响应时间从「小时/天级」降到「秒/分钟级」。
- 沉淀组织的「数据口径」，通过语义层保证同一个指标全公司算出来是一样的。

### 4.2 技术目标

- 跑通 **自然语言 → SQL → 执行 → 结果 → 洞察** 的端到端链路。
- 建立可插拔的**多数据源抽象层**与**模型适配层**两块地基。
- 用 **RAG 语义层** 显著提升复杂 Schema 下的 SQL 生成准确率。
- 实现**深度研究式分析**的多步 Agent 循环（拆解—查询—反思—汇总）。
- 产出可演进的架构，支持从「学习演示」逐步走向「生产可用」。

## 5. 能力范围（Scope）

### 5.1 In Scope（本项目覆盖）

- 多轮对话式问数（Text-to-SQL）。
- 数据源 Schema 的自动探查与向量化。
- 业务术语 / 指标口径的语义层管理。
- 查询结果以表格 + 图表（柱/折/饼）呈现。
- 复杂问题的自主拆解与多步分析（Deep-Research 式）。
- 生成 SQL 的展示、溯源与错误重试。
- 多数据源接入的抽象层设计。
- 结果洞察的自然语言总结。

### 5.2 Out of Scope（暂不覆盖，作为演进方向）

- 细粒度数据权限（行级/列级 ACL）——设计上预留，一期不实现。
- 大规模并发与多租户隔离——架构上考虑，非本期重点。
- 写入类操作（INSERT/UPDATE/DELETE）——**默认严禁**，只读分析。
- 实时数据流分析（Streaming）——面向批量/OLAP 查询。
- 训练专用 SQL 模型——完全依赖通用 LLM + Prompt + RAG。

## 6. 目标用户与典型场景

| 角色 | 诉求 | 典型提问 |
|---|---|---|
| 业务/运营 | 快速取数、看趋势 | 「上个月各地区的销售额是多少？哪个增长最快？」 |
| 数据分析师 | 探索式分析、归因 | 「为什么 3 月复购率下降？帮我拆解到品类维度看看。」 |
| 管理层 | 直接看结论与洞察 | 「给我一份本季度整体经营健康度总结。」 |
| 数据工程 | 接入数据源、定义口径 | 配置数据源连接、维护指标字典。 |

## 7. 关键成功指标（如何衡量好坏）

- **SQL 生成准确率**：在评测集上，生成 SQL 可执行且结果正确的比例（目标 ≥ 80%）。
- **端到端任务完成率**：复杂问题经过多步分析最终产出可信结论的比例。
- **幻觉率**：生成不存在字段/表/错误聚合的比例（越低越好，目标 < 5%）。
- **首 token 响应时延 / 完整回答时延**：交互体验指标。
- **口径一致性**：同一指标在不同问法下结果稳定的比例。

## 8. 项目范围约束与假设

- **假设**：底层数据源已完成基本清洗，具备可用的表结构；本项目做的是「数据消费」层而非「数据治理」层。
- **约束**：只读优先，所有生成的 SQL 必须经过安全校验（禁止 DDL/DML、限制全表扫描、超时保护）。
- **约束**：LLM 输出不可盲信，必须内置结果校验与错误重试机制。
- **假设**：单用户会话起步，多用户/鉴权作为演进项。

## 9. 里程碑与演进路线

| 阶段 | 里程碑 | 交付内容 |
|---|---|---|
| M1 · 地基 | 单数据源问数跑通 | 数据源抽象层（先支持 SQLite）+ 模型适配层 + 简易 Text-to-SQL 链路 |
| M2 · 语义层 | 准确率提升 | Schema 探查 + RAG 语义层（术语/字段含义向量化）+ SQL 校验与重试 |
| M3 · 呈现 | Web 对话产品 | FastAPI 后端 + Web 聊天前端 + 表格/图表渲染 + 查询溯源 |
| M4 · 深度分析 | Data Agent 成型 | 多步拆解的 Deep-Research 循环 + 结果洞察总结 |
| M5 · 工程化 | 走向可用 | 多数据源接入 + 会话管理 + 权限/审计预留 + 评测集 |

## 10. 风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| LLM 生成的 SQL 错误 / 幻觉 | 给出错误结论，误导决策 | Schema 严格约束 + RAG 增强 + 执行前校验 + 结果反思重试 |
| 复杂 Schema 下上下文超长 | 准确率下降、成本高 | 用 RAG 只召回相关表/字段，而非塞入全库结构 |
| 口径不统一 | 同一指标多次问结果不同 | 建立指标语义层，指标定义集中管理 |
| 误执行写操作 / 危险 SQL | 数据破坏 | 只读账号 + SQL 白名单校验 + 超时/行数限制 |
| 模型厂商锁定 | 迁移成本高 | 模型适配层抽象，接口对齐 OpenAI 协议 |

## 11. ChatBI 能力成熟度模型（L1–L5）

> 这是回答「ChatBI / Data Agent 到底需要具备什么能力」最实用的框架。任何一次产品沟通，先对齐「做到哪一级」，再谈功能细节。

| 等级 | 名称 | 能做什么 | 关键能力要求 | 本项目对应 |
|---|---|---|---|---|
| **L1** | 取数问答 | 单句问题 → 单条 SQL → 返回一张表 | 意图理解、Schema 感知、SQL 生成与执行 | M1，必达底线 |
| **L2** | 可信问答 | 结果准确、口径统一、失败会自我修正 | RAG 语义层、术语字典、SQL 校验、错误重试、澄清追问 | M2 |
| **L3** | 可视问答 | 自动选图、多轮追问、能看能导 | 图表推荐、上下文管理、溯源展示、结果导出 | M3 |
| **L4** | 分析智能体 | 面对「为什么」能自主拆解、多步查询、给出归因结论 | 问题分解、中间结果推理、反思循环、洞察生成 | M4 |
| **L5** | 生产级数据助手 | 多用户、带权限、可审计、准确率有保障 | 权限/行列级管控、审计、评测体系、并发与成本治理 | M5 及以后 |

**判读原则**：

- L1 → L2 是**从「能演示」到「能信」**的跨越，靠语义层而非换更大的模型。
- L2 → L4 是**从「答题」到「做分析」**的跨越，靠 Agent 多步循环而非单次生成。
- 多数团队卡在 L2：模型能写对 SQL，但业务口径不统一，导致「同一个指标两个人问出两个数」。

## 12. 概念辨析

这些词经常被混用，但能力和复杂度差别很大：

| 概念 | 核心能力 | 与本项目关系 |
|---|---|---|
| **传统 BI** | 预建报表/仪表盘，拖拽式配置 | 本项目要**降低**的门槛；可作为输出目的地（L5 演进） |
| **NL2SQL / Text-to-SQL** | 自然语言 → 单条 SQL | 本项目的**底层原子能力**，对应 L1 |
| **ChatBI** | 对话式取数 + 可视化 + 多轮追问 | 本项目的**产品形态**，对应 L1–L3 |
| **Data Agent** | 自主规划、多步执行、反思修正、产出洞察 | 本项目的**智能体内核**，对应 L4 |
| **语义层（Semantic Layer）** | 集中管理指标定义、口径、维度关系 | 本项目的**准确率地基**，对应 L2 |

结论：本项目 = **ChatBI 的产品外壳 + Data Agent 的推理内核 + 语义层的口径地基**，目标做到 L4，架构上为 L5 预留。

| 产品 | 特点 | 可借鉴点 |
|---|---|---|
| 阿里云 Quick BI / 帆软 FineChatBI | 国内 BI 厂商的对话式扩展 | 指标字典与口径管理的产品化形态 |

## 14. 验收标准（Definition of Done）

设计方案的验收不看代码行数，而看以下条目是否可判定：

- [ ] L1 链路在单一数据源上端到端可跑通（问题 → 结果 → 自然语言回答）。
- [ ] 复杂 Schema（≥ 20 张表）下不出现「引用不存在字段」的幻觉错误。
- [ ] 至少 1 个核心指标有语义层定义，且两种不同问法得到相同结果。
- [ ] 生成的 SQL 可展开查看并支持人工核验（溯源可见）。
- [ ] 危险操作在数据源层面被物理阻断（只读账号 / `mode=ro`）。
- [ ] L4 拆解链路对 1 个「为什么」类问题产出含归因的多步报告。
- [ ] 有一份 ≥ 30 条的评测集与准确率基线数字。
