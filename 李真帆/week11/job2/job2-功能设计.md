## 2. 用户主流程

### 2.1 基础问数流程（单次）

```
用户输入自然语言问题
        ↓
[意图识别] → 是否属于数据分析类问题？
    ├── 否 → 礼貌拒绝，引导提问范围
    └── 是 → 继续
        ↓
[RAG 语义层] → 召回相关表结构 + 字段含义 + 指标定义 + 历史相似问答
        ↓
[Prompt 组装] → 问题 + Schema + Few-shot + 约束规则
        ↓
[LLM 推理] → 生成 SQL（可能多候选）
        ↓
[SQL 校验] → 是否只读？是否引用合法表/列？是否带 LIMIT？
    ├── 不合法 → LLM 重新生成（最多 N 次）
    └── 合法 → 继续
        ↓
[数据源路由] → 确定目标数据源 → 执行 SQL → 返回结果集
        ↓
[分析层] → 结果初步解读 + 图表推荐
        ↓
[LLM 总结] → 生成自然语言结论
        ↓
输出：文字结论 + 数据表格 + 图表 + 展开查看 SQL
```

### 2.2 深度分析流程（多步 Agent 循环）

```
用户提出复杂问题（如「为什么 3 月销售额下降？」）
        ↓
[问题拆解 Agent] → 分解为子问题列表：
    ├── 1. 3 月 vs 2 月各品类销售额对比
    ├── 2. 下降幅度最大的品类是什么？
    ├── 3. 该品类哪些客户贡献下降最多？
    └── 4. 是量（订单数）降还是价（客单价）降？
        ↓
[逐步执行] → 对每个子问题走「基础问数流程」
        ↓
[反思检查] → 中间结论是否自洽？是否需要补充查询？
    ├── 不足 → 追加子问题，重新循环
    └── 充分 → 汇总
        ↓
[洞察报告 Agent] → 综合所有子结论生成归因报告
        ↓
输出：分层结论 + 支撑数据 + 洞察建议
```

### 2.3 多轮追问流程

```
用户：「各地区销售额是多少？」
系统：（返回表格 + 图）
用户：「华南地区按月份再拆一下」       ← 继承上文语义
系统：（识别上下文，修改聚合维度，重新查询）
用户：「能导出为 CSV 吗？」             ← 操作请求
系统：（触发下载，不重新查询）
```

## 3. 功能模块详细描述

### 3.1 A · 问数能力

#### A1. 意图识别

| 功能点 | 描述 |
|---|---|
| 问题分类 | 将用户输入分为：取数类 / 分析类 / 操作类（导出/可视化切换）/ 闲聊 |
| 数据源意图 | 识别问题涉及哪个数据源（多数据源场景下路由） |
| 歧义标记 | 问题过于宽泛或含糊时，触发澄清追问而非直接生成 SQL |

#### A2. Schema 感知与数据源路由

- 根据问题语义，从语义层检索**最相关的表与字段**（而非全量 Schema）。
- 多数据源时，确定目标数据源（由问题关键词 + 表名映射决定）。
- 向下游 Prompt 只提供**相关子集**，控制 Token 消耗。

#### A3. SQL 生成

输入要素（Prompt 组装）：

```
系统角色提示词
+ 相关表结构（字段名 + 业务含义注释）
+ 匹配的指标定义（如"GMV = SUM(order_amount)"）
+ Top-K 相似历史问答（Few-shot）
+ 安全约束规则（只读、必须加 LIMIT、禁止 SELECT *）
+ 用户本轮问题
+ 对话历史（多轮场景）
```

输出格式（结构化 JSON）：

```json
{
  "sql": "SELECT ...",
  "reasoning": "我需要找出各地区上月的订单总额...",
  "confidence": "high | medium | low",
  "needs_clarification": false,
  "clarification_question": null
}
```

#### A4. SQL 执行与结果返回

- 通过数据源抽象层下发，统一返回标准结果集格式（列名 + 行数据）。
- 执行超时（默认 15s）、行数上限（默认 1000 行）保护。
- 执行报错时，将错误信息连同原始 SQL 重新交给 LLM 做修正重试。

#### A5. 结果自然语言化

- 将原始数据交给 LLM，以简洁中文写出「结论是什么 + 关键点在哪里」。
- 数据量小时直接列举；数据量大时给出 Top-N + 汇总统计。

---

### 3.2 B · 语义层能力（RAG 增强）

#### B1. Schema 向量化索引

**目标**：把数据库结构「翻译」成大模型能理解的语义知识。

索引内容单元（每个单元一条向量）：

```
表级：{表名, 业务描述, 主要用途}
列级：{表名.列名, 数据类型, 业务含义注释, 示例值, 是否可作为维度/度量}
关系级：{表A.列X → 表B.列Y, 关联类型(1:1/1:N), 业务含义}
```

更新时机：数据源接入时 / 手动刷新 / Schema 变更监听。

#### B2. 业务术语 / 指标字典

**目标**：保证口径统一，消除「不同人问出不同 SQL」的问题。

示例：

| 术语 | 定义 | 计算公式 / SQL 片段 | 涉及表 |
|---|---|---|---|
| GMV | 总交易额 | SUM(orders.amount) WHERE status != 'cancelled' | orders |
| 复购率 | 2 次及以上消费的客户占比 | COUNT(DISTINCT user_id HAVING cnt>=2) / COUNT(DISTINCT user_id) | orders, users |
| 客单价 | 平均每笔订单金额 | AVG(orders.amount) | orders |

词典来源：系统管理员手动录入 + 历史有效问答自动挖掘。

#### B3. 历史问答检索

**目标**：把验证过的「好问答」存起来，作为 Few-shot 注入 Prompt，持续提升准确率。

存储单元：`{问题原文, 标准 SQL, 结果摘要, 业务标签}`

检索时机：每次新问题时，语义检索最相似的 Top-3 历史问答，作为 Few-shot 示例。

#### B4. 歧义消解与澄清追问

当问题满足以下任意条件时，系统不直接生成 SQL，而是先追问：

- 涉及多个数据源，无法自动判断目标。
- 指标口径有多种理解（如「活跃度」可以是 DAU 也可以是登录次数）。
- 时间范围缺失（「最近」= 最近 7 天 / 本月 / 本季度？）。
- 数据量维度过多，结果可能过于庞大。

### 3.3 C · 深度分析能力

#### C1. 复杂问题自动拆解

识别问题是否需要多步分析（标志词：「为什么 / 原因 / 归因 / 对比 / 趋势 / 拆解到」）。

拆解 Agent 输出：

```json
{
  "is_complex": true,
  "sub_questions": [
    {"id": 1, "question": "3月各地区销售额环比变化", "depends_on": []},
    {"id": 2, "question": "下降最大的地区的品类构成", "depends_on": [1]},
    {"id": 3, "question": "下降品类的订单量 vs 客单价变化", "depends_on": [2]}
  ]
}
```

#### C2. 多步查询与中间结果缓存

- 按依赖顺序依次执行子问题。
- 中间结果缓存（Session 级），后续子步骤可直接引用（如按步骤 1 确认的地区做步骤 2 的过滤条件）。
- 每步完成后，将结论写回「分析状态」供后续步骤使用。

#### C3. 结果反思与错误重试

每步执行后，反思 Agent 检查：

- 执行是否报错？→ 触发 SQL 修正重试。
- 结果是否符合预期范围？（如占比之和是否接近 100%）
- 结论是否与问题相关？→ 若无关，重新拆解或澄清。

#### C4. 数据洞察生成

对最终结果集，由 LLM 识别：

- **趋势**：递增/递减/周期，关键拐点。
- **异常**：显著偏离均值的数据点。
- **归因**：导致变化的主要维度贡献分解（如「A 品类贡献了 60% 的下降」）。

#### C5. 分析结论汇总报告

多步分析结束后，产出结构化报告（Markdown 格式），包含：

```
## 结论摘要
（一句话直接回答主要问题）

## 主要发现
1. 发现 A（支撑数据：表格/图）
2. 发现 B（支撑数据）
...

## 建议行动
- 建议 1
- 建议 2
```

### 3.4 D · 呈现能力

#### D1. 多轮对话管理

- 维护 `session_id` 对应的对话历史。
- LLM 组装 Prompt 时注入最近 N 条历史，保证指代消解（「华南地区」→ 上一轮的华南）。
- 支持用户指令：「清空上下文 / 重新开始」。

#### D2. 数据表格展示

- 查询结果以可排序的轻量表格呈现（支持 Web 端直接交互）。
- 大数据量时前端分页 / 虚拟滚动，不全量渲染。

#### D3. 图表推荐与渲染

图表推荐逻辑（Agent + 规则混合）：

| 数据特征 | 推荐图表 |
|---|---|
| 分类 + 数值，分类数 < 8 | 柱状图 |
| 时间序列 + 数值 | 折线图 |
| 部分占比（和 = 100%）| 饼图 / 环形图 |
| 两维交叉数据 | 热力图 / 分组柱状图 |
| 多维对比 | 雷达图 / 平行坐标（进阶） |

图表以 JSON Spec（ECharts 兼容格式）由 LLM 生成，前端统一渲染。

#### D4. 查询溯源

每条回答下方提供「查看 SQL」展开面板，包含：

- 最终执行的 SQL 语句（高亮）。
- 执行耗时与返回行数。
- 引用的 Schema 片段（哪些表/字段）。
- 历史问答匹配情况（用了哪条 Few-shot）。

#### D5. 分析过程可视化

深度分析模式下，Agent 的每一步思考/操作以**流式进度面板**展示：

```
[步骤1] 拆解子问题 → 完成 ✓
[步骤2] 执行：各地区环比 → 完成 ✓
[步骤3] 执行：下降地区品类分解 → 进行中...
[步骤4] 等待步骤2结果 → 待执行
[步骤5] 生成洞察报告 → 待执行
```

### 3.5 E · 工程能力

#### E1. SQL 安全护栏

校验规则（可配置）：

- **语法白名单**：只允许 SELECT / WITH；禁止 INSERT/UPDATE/DELETE/DROP/TRUNCATE 等。
- **表/列合法性**：SQL 中引用的表名和列名必须在 Schema 中存在（防幻觉）。
- **强制 LIMIT**：若 SQL 未带 LIMIT，自动追加 `LIMIT 1000`（可配置）。
- **禁止 SELECT ***：要求明确列出字段（性能 + 可读性）。

#### E2. 查询超时与行数限制

- 每个数据源配置查询超时（默认 15s，超时则中断并提示精简问题）。
- 结果集行数上限（默认 1000 行，超出截断并提示用户加过滤条件）。

#### E3. 数据源连接管理

- 连接池（针对关系型数据库）+ 单文件模式（针对 SQLite）。
- 数据源配置热加载（新增/修改/禁用），不重启服务。
- 定期健康检查，不可用数据源自动下线并告警。

#### E4. 会话与历史记录持久化

- 用户会话（含对话历史、查询结果快照、分析中间态）持久化到文件或数据库。
- 支持按时间检索历史会话（为「历史记录」功能做准备）。

#### E5. 操作审计日志（预留）

- 记录每次请求的：时间戳、用户标识、问题、生成 SQL、执行结果摘要、耗时。
- 为后续权限管控、质量分析提供数据基础。

## 5. 异常处理与降级策略

| 异常 | 处理策略 |
|---|---|
| LLM 生成 SQL 报错 | 错误信息反馈 LLM，最多重试 3 次，仍失败则告知用户无法解析 |
| 语义层召回为空（无相关表） | 降级提示用户：「未能找到相关数据，请确认问题涉及的数据范围」 |
| 数据源连接失败 | 提示用户数据暂不可用，同时触发电平告警（E3） |
| 查询超时 | 中断执行，建议用户缩小时间范围或加过滤条件 |
| 结果行数超限 | 截断 + 提示，不阻断，给出过滤建议 |
| 深度分析中间步骤失败 | 跳过失败步骤，用已有结果汇总，在报告中标注缺失部分 |

## 6. 端到端走查示例（L1 单次问数）

> 以下用一个通用零售库演示一次完整链路，让前面所有功能描述有可对照的具体形态。
>
> 示例 Schema：`orders(order_id, customer_id, amount, status, order_date)`、`customers(customer_id, name, region, register_date)`、`products(product_id, name, category, price)`、`order_items(item_id, order_id, product_id, quantity)`

### 步骤 1｜用户输入

```
上个月各地区的 GMV 是多少？哪个最高？
```

### 步骤 2｜IntentAgent 输出

```json
{
  "intent": "取数",
  "is_complex": false,
  "entities": {
    "metric": "GMV",
    "dimension": "地区",
    "time_range": "上个月（需具体化为 2026-09）",
    "sort": "降序取最大"
  }
}
```

### 步骤 3｜语义层召回结果

召回的术语定义（命中指标字典，这是口径统一的关键）：

```
GMV = SUM(orders.amount) WHERE orders.status != 'cancelled'
```

召回的相关表：`orders`、`customers`（含外键关系 `orders.customer_id → customers.customer_id`）。

未命中的表（`products`、`order_items`）不注入 Prompt，控制 Token。

### 步骤 4｜SQLAgent 生成的 SQL

```sql
SELECT
  c.region,
  SUM(o.amount) AS gmv
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.status <> 'cancelled'
  AND o.order_date >= '2026-09-01'
  AND o.order_date <  '2026-10-01'
GROUP BY c.region
ORDER BY gmv DESC
LIMIT 1000;
```

安全校验通过：只读、表列均存在、含 LIMIT。

### 步骤 5｜执行结果

| region | gmv |
|---|---|
| 华东 | 1,284,500.00 |
| 华南 | 968,320.50 |
| 华北 | 752,180.00 |
| 西南 | 310,440.20 |

耗时 42ms，返回 4 行。

### 步骤 6｜AnalysisAgent 输出的图表 Spec

```json
{
  "chart_type": "bar",
  "reason": "分类数值对比，分类数 = 4 (<8)，适用柱状图",
  "title": "2026 年 9 月各地区 GMV",
  "x": ["华东", "华南", "华北", "西南"],
  "y": [1284500, 968320.5, 752180, 310440.2]
}
```

### 步骤 7｜最终自然语言回答

> 2026 年 9 月各地区 GMV（已排除取消订单）：**华东最高，约 128.5 万**，占四区总量的 36%。
>
> 排序为：华东 128.5 万 > 华南 96.8 万 > 华北 75.2 万 > 西南 31.0 万。
>
> 华东比第二名华南高出约 32.7%。【查看 SQL】【数据源：orders + customers】

## 7. 澄清与多轮追问示例

### 7.1 歧义澄清（不直接猜）

```
用户：活跃度怎么样？
系统：「活跃度」在指标字典中有两种口径，请确认：
      1) DAU（日均活跃用户数）
      2) 登录次数 / 天数
      另外请补充时间范围（近 7 天 / 本月 / 本季度？）
用户：DAU，本月
系统：（正常走取数链路）
```

**设计原则**：宁可多反问，不可默默猜错。猜错的代价是用户拿着错数据做决策。

### 7.2 多轮指代消解

```
轮1 用户：各地区 GMV 多少？
    系统：（返回四行数据 + 柱状图）
轮2 用户：华南再按月拆一下
    系统：识别为「继承上文指标=GMV、过滤 region='华南'、维度改为月份」
          → 仅重生 SQL，不重复确认指标口径
轮3 用户：能不能导出
    系统：识别为操作类意图，直接对轮2 结果导出 CSV（不重新查询）
轮4 用户：重新开始，看看商品维度
    系统：清空上下文，回到全量 Schema 检索
```

## 8. 深度分析走查示例（L4）

### 输入

```
为什么 9 月 GMV 环比 8 月下降了？
```

### 步骤 1｜ResearchAgent 拆解

```json
{
  "is_complex": true,
  "plan": [
```

### 步骤 2｜逐步执行与反思

| 步骤 | 中间结论 | 反思检查 |
|---|---|---|
| 1 | 9 月 GMV 128.5万，8 月 162.0万，环比 **-20.7%** | 降幅显著，需归因 → 继续 |
| 2 | 华东贡献总降幅的 **58%** | 地区拆解之和≈总降幅，自洽 ✓ |
| 3 | 华东降幅中 72% 来自「数码」品类 | 首次执行报错（字段名幻觉）→ 重试成功 |
| 4 | 数码品类订单量 -35%，客单价 +2% | 结论：**是量不是价** |
| 5 | 8 月贡献 Top3 客户中 2 家 9 月零消费 | 补充查询确认非数据缺失 ✓ |

### 步骤 3｜洞察报告输出

```markdown
## 结论摘要
9 月 GMV 环比下降 20.7%（-33.5 万），**主因是华东地区数码品类订单量锐减**，
而非客单价下降，其中 2 家大客户停止消费贡献了 41% 的降幅。

## 主要发现
1. **地区集中度**：华东贡献总降幅的 58%（-19.5 万）。
2. **品类集中度**：华东降幅的 72% 来自数码品类。
3. **量价分解**：数码品类订单量 -35%、客单价 +2% → 典型流量/客户问题，非价格问题。
4. **客户归因**：Top3 客户中 2 家 9 月零消费，合计影响 -13.7 万。

## 建议行动
- 优先联系 2 家停止消费的存量大客户，确认是否流失。
- 排查数码品类 9 月是否有缺货/下架/活动结束等供给因素。
- 建议监控项：数码品类周度订单量（建议设为阈值告警）。

## 口径与局限
- GMV = SUM(orders.amount) WHERE status != 'cancelled'。
- 本报告基于 orders/customers 表，未含退款时间差影响。
```

**注意最后一段「口径与局限」**：这是 L4 与 L1 的关键区别 —— 结论附带的假设与边界必须声明，避免用户过度信任。

## 9. 非功能需求

功能需求之外，以下指标决定产品能不能真正用起来：

| 类别 | 需求 | 具体指标 |
|---|---|---|
| **性能** | 简单取数端到端时延 | P90 ≤ 5s（含 LLM 推理） |
| **性能** | 深度分析完成时延 | P90 ≤ 60s，且**必须流式展示中间进度** |
| **性能** | 首字节响应 | ≤ 1.5s（先返回「已理解问题」，避免白屏等待） |
| **准确性** | 简单问题 SQL 正确率 | ≥ 90% |
| **准确性** | 复杂 Schema 下 SQL 正确率 | ≥ 75% |
| **准确性** | 幻觉率（不存在的表/列） | ≤ 3% |
| **可靠性** | LLM 服务不可用时 | 降级提示，不崩溃；已查结果仍可查看 |
| **安全性** | 写操作 | 100% 拦截（双保险：应用层校验 + 数据源只读） |
| **可解释性** | 每条结论 | 必须可回溯到具体 SQL 与数据行 |
| **可观测性** | 全链路 | 每步耗时、Token 消耗、重试次数可查 |
| **成本** | 单次问答 Token | 简单问题 ≤ 4K Token（靠 RAG 只召回相关表控制） |
| **易用性** | 零 SQL 知识 | 主流程不需用户看到 SQL 也能完成取数（SQL 默认折叠） |

## 附录 A・术语表

> 面向不熟悉 ChatBI / Data Agent 的读者，按阅读顺序排序。

| 术语 | 含义 | 为何重要 |
|---|---|---|
| **Text-to-SQL / NL2SQL** | 自然语言转结构化查询语句 | ChatBI 的底层原子能力 |
| **Schema** | 数据库结构：表、列、类型、关系 | LLM 不看 Schema 就只能「猜」表名，必出幻觉 |
| **语义层（Semantic Layer）** | 业务口径的集中定义层（指标、维度、术语） | 保证「同一个指标全公司算出来一样」 |
| **RAG**（检索增强生成） | 先从知识库检索相关内容，再交给 LLM 生成 | 把「全库 Schema」换成「相关 Schema」，降 Token 提准确 |
| **Embedding / 向量化** | 把文本转为多维向量，用相似度做语义检索 | 支持「问销售额」能召回到 `gmv` 字段这种非字面匹配 |
| **Few-shot** | 在 Prompt 里给几个示例 | 历史验证过的问答作示例，是提准确率性价比最高的手段 |
| **幻觉（Hallucination）** | 模型编造不存在的表名/字段名/数据 | 数据分析场景的头号风险，必须工程手段拦截 |
| **Agent** | 能自主「思考→调用工具→观察结果→再决策」循环的 LLM 程序 | 从「答题」升级到「做分析」的关键 |
| **ReAct** | Reasoning + Acting，推理与行动交替的 Agent 范式 | 多步分析循环的理论基础 |
| **Tool Calling / Function Calling** | LLM 输出结构化调用请求（如「执行这条 SQL」） | 让模型能安全地驱动外部能力 |
| **DAG**（有向无环图） | 带依赖关系的任务拓扑 | 描述「先算总量、再拆维度」的子问题依赖 |
| **SSE**（Server-Sent Events） | 服务端向浏览器流式推送事件 | Agent 耗时长的必要交互手段 |
| **口径** | 指标的计算边界与定义（是否含退款/取消等） | 80% 的数据争议本质是口径争议 |
| **OLAP / OLTP** | 分析型查询 / 事务型查询 | 解释了为何分析查询必须加超时保护 |
| **只读账号** | 数据库层面不具备写权限的连接账号 | SQL 安全的最硬兜底（比应用校验更可靠） |
