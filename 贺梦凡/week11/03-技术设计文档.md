## 1. 架构

```text
对话界面
    |
    v
问数 API（FastAPI）
    |
    +-- 会话存储
    +-- 权限与指标
    |
    v
SQLAgent 编排
    |-- DBParser        解析、校验、执行
    |-- 模型适配层       生成、改写、汇总
    |-- 规则改写         补充分组字段
    |
    +-- 审计日志
    +-- 评测任务

外部问题 -> MCP 工具（股票、新闻） -> 同一汇总步骤
```

原型已经把编排放在进程内：`SQLAgent` 调用 `DBParser` 和 OpenAI 兼容客户端。下一阶段把 `run()` 放到 FastAPI 后面，会话和审计落库。股票助手里的 MCP、路由和对话列表按同一边界接入，不另做一套问数流程。

数据流：

1. API 收到问题和对话标识。
2. 用最近 10 轮把追问补全。
3. 按用户权限裁剪表结构。
4. `select_tables` 选表并 `_connect_tables` 补路径。
5. `generate_sql` 生成查询。
6. `repair_sql` 循环调用 `check_answer_sql` 和 `rewrite_sql`。
7. `execute_sql` 返回 `DataFrame`。
8. `summarize` 生成结论。
9. 写入审计，返回结论、列、行、SQL 和选表理由。

## 2. 原型中的模块

| 代码 | 职责 | 对应功能 |
| --- | --- | --- |
| `DBParser` | 连接 SQLite，统计字段，读取外键和样例 | F1 |
| `DBParser.check_sql` | `EXPLAIN` 前先做只读判断 | F6 |
| `DBParser.execute_sql` | 最多取 100 行 | F8 |
| `SQLAgent.select_tables` | 选表、关键词兜底、补连接路径 | F4 |
| `SQLAgent.generate_sql` | 按结构和指标提示生成 SQL | F5 |
| `SQLAgent.check_answer_sql` | 语法、相关表、聚合、分组字段 | F6 |
| `SQLAgent.rewrite_sql` | 把错误和表结构交回模型 | F7 |
| `_add_group_columns_to_select` | 不调用模型，把分组字段补进 SELECT | F7 |
| `SQLAgent.summarize` | 根据前 30 行写结论 | F9 |
| `SQLAgent.run` | 按七步打印并返回结果 | 编排 |
| `resolve_llm_config` | 有密钥走云端，否则走本机 Ollama | 模型适配 |

`run()` 的返回包含问题、选中表、扩展表、最终 SQL、每一轮校验、结果表和结论。API 层直接使用这个结构，不再解析控制台输出。

## 3. 模型适配

所有生成式步骤都走 OpenAI Chat Completions 兼容接口。

| 用途 | 配置 | 当前状态 |
| --- | --- | --- |
| 默认云端 | `OPENAI_API_KEY`，百炼兼容地址，模型 `qwen-plus` | 课程密钥返回 401 |
| DeepSeek | `OPENAI_BASE_URL=https://api.deepseek.com`，模型 `deepseek-chat` | 课程密钥返回 401 |
| 豆包 | 火山引擎 Ark 兼容地址，模型用接入点 ID | 无密钥，未接通 |
| ChatGPT | `https://api.openai.com/v1` | 无密钥，未接通 |
| 本地 | `http://127.0.0.1:11434/v1`，`qwen3:0.6b`，关闭思考模式，上下文 16384 | 可用 |

调用参数：

- SQL 生成和改写：`temperature=0.1`，`max_tokens=1024`。
- 汇总：`temperature=0.2`。
- 本地 Qwen 额外关闭思考模式，避免思考文本混进 SQL。
- 返回内容去掉 `<think>` 段，再抽取 JSON 或 SQL 代码块。

模型分工是部署策略，不是某一家模型已经同意的方案：

- SQL 生成和改写使用结构化输出比较稳定的模型。
- 中文汇总可以使用另一个模型。
- 评测只比较结果和标准答案，不让生成模型判断自己是否正确。
- 云端失败时可以降级到本地模型，但评测正确率低于阈值时，接口返回「模型不可用」，不把不稳定 SQL 交给用户。

本地 `qwen3:0.6b` 能完成 Chinook 标准题，是因为提示词里带了同型 SQL，并且校验会拒绝漏表、漏聚合和漏分组字段。换库以后这些提示要改成该库的指标定义，不能继续写死 Chinook 表名。

## 4. 校验与执行

只读判断在应用层完成，数据库账号后续也使用只读账号，两层同时存在。

`EXPLAIN` 使用短连接。SQLite 通过 SQLAlchemy 2.x 的 `Connection` 执行，查询后回滚。不使用 SQLAlchemy 1.x 的 `Engine.execute`。

执行层限制：

- 单条语句。
- 最多返回 100 行，超出则 `truncated=true`。
- 汇总只看前 30 行，并告知截断。
- 连接串由服务端配置，不接受用户随问题传入任意数据库 URL。

Chinook 的业务关系写在指标和提示中，关键一条是曲目销售额走明细单价乘数量，艺术家必须经过 `albums`。这是校验规则，不只是提示词希望。

## 5. 逻辑数据

原型阶段结构在内存里。M2 起使用下面这些表，可以和股票助手的会话库放在一起，但问数审计单独成表。

`datasource`

| 字段 | 含义 |
| --- | --- |
| id | 数据源 |
| name | 显示名 |
| db_url | 服务端保存的连接串 |
| dialect | sqlite / mysql |

`metric`

| 字段 | 含义 |
| --- | --- |
| name | 如「曲目销售额」 |
| expression | SQL 聚合表达式 |
| required_tables | 有序表名 |
| description | 给模型和用户看的口径 |

`conversation` / `message`

| 字段 | 含义 |
| --- | --- |
| conversation_id | 对话 |
| role | user / assistant |
| content | 用户原话或结论 |
| rewritten_question | 补全后的问题 |
| sql | 最终 SQL |
| tables | 扩展后的表 |

`query_trace`

| 字段 | 含义 |
| --- | --- |
| trace_id | 一次问答 |
| user_id | 用户 |
| attempts | 每一版 SQL 和校验结果 |
| row_count | 返回行数 |
| truncated | 是否截断 |
| model | 模型名 |
| latency_ms | 分步耗时 |
| created_at | 查询时间 |

`eval_case`

| 字段 | 含义 |
| --- | --- |
| question | 标准问法 |
| expected_sql_check | 结果应满足的断言，如第一行、第一列的值 |
| forbidden | 必须拒绝的 SQL 样例 |

断言检查结果值，不要求生成的 SQL 文本与标准答案逐字相同。

## 6. 接口

M2 的问数接口：

`POST /api/chat`

```json
{
  "conversation_id": "可选，空则新建",
  "question": "每个国家分别有多少位客户？"
}
```

```json
{
  "conversation_id": "conv_01",
  "rewritten_question": "每个国家分别有多少位客户？按客户数从高到低排列。",
  "tables": ["customers"],
  "sql": "SELECT ...",
  "columns": ["country", "customer_count"],
  "rows": [["USA", 13]],
  "truncated": false,
  "summary": "客户数最多的国家是 USA，有 13 位客户。",
  "trace_id": "tr_01"
}
```

失败时 HTTP 200 返回业务错误，避免前端把校验失败当成服务崩溃：

```json
{
  "error": "sql_validation_failed",
  "message": "SQL 校验失败，已达到重试上限",
  "trace_id": "tr_02"
}
```

其他接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/conversations` | 当前用户的对话列表 |
| GET | `/api/conversations/{id}` | 对话内容，含 SQL |
| GET | `/api/traces/{id}` | 审计回放，限分析师和审计角色 |
| POST | `/api/eval/run` | 跑 F14 题集，返回正确率和平均改写次数 |

股票工具继续由 MCP 提供。问数 API 在识别到行情类问题后调用 MCP，不把行情 SQL 硬写进 Chinook。

## 7. 安全

| 控制 | 做法 |
| --- | --- |
| 写操作 | 应用层拒绝 DML / DDL；数据库使用只读账号 |
| 多语句 | 去掉注释后仍含分号则拒绝 |
| 提示注入 | 用户问题只作为「问题」字段，不拼接成可执行 SQL |
| 连接串 | 只来自服务端配置 |
| 权限 | 不可见表不进入提示词 |
| 脱敏 | 样例值和结果按列配置遮盖 |
| 密钥 | 模型密钥只放环境变量，不写进仓库和新的设计文档 |
| 审计 | 记录 SQL 和校验错误，不记录模型密钥 |

本地 Qwen 把加密、访问控制和异常检测列为容易漏掉的能力。第一期落实访问控制和审计；传输使用 HTTPS，SQLite 文件的磁盘权限由部署环境限制。异常检测先记录校验失败率突增和空结果率突增，不在对话链路里做独立风控模型。

## 8. 可观测与时限

每次 `trace` 记录选表、生成、每一次校验、改写、执行、汇总的耗时。

时限按复杂度，而不是统一 3 秒：

| 类型 | 目标 |
| --- | --- |
| 已缓存结构上的单表聚合，云端模型 | 数秒级 |
| 需要改写的跨表问题 | 15 秒内给出最终结果或明确失败 |
| 本地 0.6B 模型 | 作为开发和降级路径，不承诺 3 秒 |

评测看正确率，不把时限放宽到可以反复盲试。改写上限保持 4 次校验。

## 9. 部署

开发部署：

- Python 3.12。
- 依赖见 `Week12/04_SQL-Code-Agent-Demo/requirements.txt`：SQLAlchemy、pandas、openai、tabulate。
- 数据库文件 `chinook.db` 与 `sql_agent.py` 同目录。
- 本机 Ollama 提供 `qwen3:0.6b`。
- 运行：`python sql_agent.py --demo`，或对单题传入问题。

目标部署与股票助手对齐：

- FastAPI 提供问数、用户和会话接口。
- MCP 提供股票等外部工具。
- 对话界面展示结论、表格和 SQL。
- 模型地址用环境变量切换，应用镜像不包含密钥。

## 10. 后续实现顺序

1. 把 `SQLAgent.run()` 包成无控制台副作用的函数，返回值已足够支撑 API。
2. 增加会话和 `query_trace` 落库。
3. 增加 F3，使追问先改写再进入现有七步。
4. 把 Chinook 专用提示收进 `metric` 配置，换数据源时只换口径，不改编排。
5. 接入只读账号、列权限和 F14 回归脚本。
6. 云端密钥可用后，用同一评测集比较 DeepSeek、Qwen、豆包和 ChatGPT，保留正确率最高且不编造数字的组合。
