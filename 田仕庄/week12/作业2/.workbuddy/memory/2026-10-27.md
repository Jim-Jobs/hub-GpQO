## 方案 v1.4：真机验证推翻 v1.3 核心设计（最重要）

用户提供 key（已写入 `00-sql-agent/.env`，gitignore 第 17 行忽略，`git check-ignore` 验证过）。真机实测结论：

**致命发现**：`with_structured_output(method="function_calling")` 在 DeepSeek 思考模式下**必然 400**：
```
Thinking mode does not support this tool_choice
```
根因：LangChain 把 `tool_choice` 钉成 `{"type":"function","function":{"name":"X"}}`，而思考模式只接受 `auto`/`required`。
**现有 openai-agents 能正常跑（4.4s/答案正确），正是因为它没强制函数名** —— 若按 v1.3 实现，会把能跑的系统改成跑不起来。

**已验证可行的替代**：
```python
llm.bind_tools([Schema], tool_choice="auto") | PydanticToolsParser(tools=[Schema]) | unwrap
```
- auto/disabled 两种 thinking 模式均通过，0.9~1.6s
- `PydanticToolsParser` 返回 list，需 `unwrap` 取 `[0]`，空列表抛 TypeError（与现有行为一致）
- 完整生产形态（PROMPT|bind_tools|parser|unwrap）已验证，含无关问题短路

实测矩阵：
| 路径 | thinking 开 | thinking 关 | 耗时 |
|---|---|---|---|
| with_structured_output(function_calling) | ❌400 | ✅ | 1.0s |
| with_structured_output(json_mode) | ✅ | 未测 | 3.3s |
| bind_tools(auto)+PydanticToolsParser | ✅ | ✅ | 0.9~1.6s |
| 裸 response_format=json_object | ✅ | 未测 | 2.0s |

其他实测：`GET /models` → `['deepseek-flash','deepseek-v4-pro']`（佐证模型名结论）；`reasoning_tokens=30`（思考模式确为默认开启）；`ChatOpenAI` 无 `timeout` 字段，须用 `request_timeout`。

**基线已抓**：`tmp/baseline/baseline_openai_agents.json`，5 问全成功、0 修复、4.4~7.1s，无关问题正确短路。

方案改动：§7.2 整节重写（含实测矩阵与降级预案）、§6.3 新增 `structured()`/`_unwrap()`、§4/§5/§6.5 改链构造、测试改 3 个新增用例（含 `test_unwrap_rejects_empty`）、R1/R7/R13 更新、决策表加 #7、阶段 0 全部完成、工作量 10.8h。git `087fa4c`，pytest 21 passed。

## 缺陷审计（用户："帮我测试一下，检查是否有bug"）

基线复现：24 passed / ruff 全绿 / 从仓库外跑同样 24 passed。真实链路 **无法联调**：`.env` 里 `OPENAI_API_KEY`（40 位、`sk-` 前缀、尾号 `xxxx`）被 DeepSeek 判 401 `invalid`，`python -m sql_agent "总共有多少张专辑？"` 直接降级返回 error。→ 需要用户重新提供有效 key 才能复验真机。

改用「脚本化假模型 + 真实 prompt/`PydanticToolsParser`」驱动整条链（现有单测把 4 个链工厂全 mock 掉，prompt 模板与解析层从未被覆盖）。探针留在 `00-sql-agent/tmp/probe_bugs{,2,3,4}.py`。

**已确认缺陷（按严重度）**
1. `validator.py:18` 禁用词含 `replace` → 合法 `REPLACE(x,'a','b')` 被判 `unsafe`。后果链（探针 3-C 复现）：生成被拒 → 改写链放弃该变换、给出语义不同的 SQL → 门禁通过 → 用户拿到静默错误的答案（rephrase 失败但 `caveats` 为空）。修法：从集合删 `replace`（`REPLACE INTO` 已被「必须 SELECT/WITH 开头」拦住）。
2. 结构化输出解析失败 = 整次查询失败且不重试：模型漏必填字段（`models.py:14` `reason`、`:23` `sql` 无默认值）时 pydantic ValidationError 原样出现在 `answer` 里（连 errors.pydantic.dev 链接都吐给用户）；模型不调工具时 `_unwrap` 抛 TypeError。位置 `workflow.py:311/418/456`。
3. `validator.py:117` 分号判定在 `normalize_sql` 之后 → `SELECT 1; -- 注释` 被误判「多语句」。
4. `workflow.py:342` 把写给模型的修复反馈当 `clarification_question` 返给用户（探针 3-F：`无法确定有效的查询表：所选表之间没有外键连接，请重新选择可以 JOIN 的表`）。
5. `executor.py:73` `row_count=len(rows)`，截断时是 200 而非真实行数；汇总 prompt 的「返回行数：200」会诱导模型说"共 200 行"。
6. `config.py` 数值环境变量无夹逼：`MAX_REPAIR_ATTEMPTS=-1` → `answer="SQL 执行失败。"`、`error="unknown error"`（完全不可定位）；`MAX_ROWS=0` → 有数据也答"未查询到"；`QUERY_TIMEOUT=-5` → 立即超时。
7. 低危：`sqlite_master` / `pragma_table_info()` 可读（后者还绕过 PRAGMA 拦截）；选表结果未去重，`render_schema(["albums","albums"])` prompt 翻倍。

**验证过没问题的部分**：只读连接（写操作/DDL 被拒）、超时（progress_handler 真生效，code=timeout）、截断（200/201 边界正确）、空结果短路、选表不连通重试 1 次、问题含 `{}`/`%`/引号不触发模板注入、11 张表行数与外键（11 条）与 AGENTS.md 完全一致、汇总失败降级表格正常、CLI 无 key/LLM 不可达/空 stdin 三条路径输出合法 JSON 且退出码正确、从任意 cwd 可运行。
