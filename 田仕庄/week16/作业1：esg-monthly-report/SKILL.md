# ESG 月报生成 Skill

给定「客户公司 + 报告月份」，编排引擎完成 检索 → 筛选 → 总结 → 成文 → 质检，交付可直接进入人工复核的月报初稿。

职责边界见 README §2：**检索 / 打分 / 渲染等确定性逻辑全部在引擎（`scripts/`），本文件只负责触发判断、流程编排、质检、措辞与合规。** 不要在对话里手工替代引擎检索、打分或拼报告。

## 1. 触发与不触发

**触发**（示例）：

- 「帮我生成中国神华 2026 年 10 月的 ESG 月报」
- 「跑一下神华上个月的 ESG 跟踪」
- 「用这个 Skill 给 A 公司出 2026-11 月报」

**不触发**：

- 单条政策/新闻的解读、答疑 → 直接回答，不走流水线。
- 非上市公司、无明确月份的泛化需求 → 先追问客户与月份，再判断。
- 用户只要一份「近年 ESG 综述」→ 说明本 Skill 只做按月窗口的报告。

## 2. 开工前确认（三要素）

| 要素 | 规则 | 缺省处理 |
|---|---|---|
| 客户 | 映射到 `config/client_<slug>.yaml`；不存在则不得运行 | 追问客户名；如需新建，按 `config/client_shenhua.yaml` 结构起草并列出待确认字段（行业口径、对标清单、关键词、合规红线） |
| 月份 | `YYYY-MM`（北京时间自然月；运行时机与窗口口径见 README §8.1） | 缺省取上一个自然月 |
| 格式 | `html` 必选，`docx` 可选 | 缺省 `html` |

时间窗口、去重口径由引擎按 README §8.1 处理，**不要在 Skill 层重复计算**。

## 3. 前置检查（顺序执行，任一失败即停）

1. `config/.env` 存在且含 `SEARCH_API_KEY`、`SEARCH_API_PROVIDER`、`LLM_API_KEY`、`LLM_MODEL`（字段说明见 README §7.3）。
   缺失 → 停止并把缺失变量名告知用户，**不得用编造数据继续**。
2. 客户配置文件存在；`config/sources.yaml` 存在。
3. 若客户画像缺 `red_lines` / `keywords` / `peers`，先与用户确认补齐，再运行。

## 4. 执行流程

```bash
conda activate py312
python scripts/run.py --client shenhua --month 2026-10 --format html,docx
```

1. **运行引擎**（等价于上表命令）。退出码 2 = 缺 Key，按 §3 处理；其他非零退出如实转述错误，不要绕开。
2. **读取产物**：`output/<client>/<month>/` 下的 `report.html`、`report.docx`（如导出）、`review_checklist.md`、`summarized.json`。
3. **Skill 层质检**：按 §6 逐项核对 `summarized.json` 与复核清单；不合格项要么让用户确认后接受，要么指出具体条目，不擅自改写引擎产物。
4. **交付说明**：列出产物路径、待核实/待总结条数、信息缺口、以及需要人工复核的重点。

无需 Key 的验证手段：`python -m pytest tests/`（离线、必须全绿）。测试通过不等于端到端跑通，没有真实运行就不要声称报告已生成。

## 5. 影响等级与措辞规则（本文件下发，引擎不硬编码）

**影响等级**：

| 等级 | 判定标准 |
|---|---|
| 高 | 直接影响评级 / 合规 / 重大经营：强制性政策落地、监管处罚、评级下调、重大安全事故、重大资产变动 |
| 中 | 行业趋势、同业重要动作、标准征求意见稿、影响成本结构的市场机制变化 |
| 低 | 一般舆情、会议活动、科普宣传、对企业无直接经营影响的动态 |
| 待核实 | 来源不可访问、事实无法交叉确认 → 单列，**不猜等级** |

**每条信息必须满足四要素**：来源 + 日期 + 影响等级 + 对客户影响一句话。

**一句话影响的写法**：

- 只陈述「事实 → 影响路径」，例如「办法提高产能储备披露要求，公司需评估现有公告口径」。
- 不预测政策走向，不评论短期煤价，不编造数字/时间/表态。
- 建议颗粒度：战略级 + 执行级各 1 条，并标注「机会 / 风险」（写作规范见 README §10）。

## 6. 交付前质检清单

- [ ] 每条收录信息四要素齐全，来源链接可点击且可访问；不可访问的已移入「待核实」并附原因。
- [ ] 来源可追溯率 ≥ 95%（以 `review_checklist.md` 统计为准）；不满足时向用户明示差距，不隐藏。
- [ ] 信息缺口（检索失败 / 无覆盖）已单列，未用推测内容填补。
- [ ] 待总结 / 待核实条目已计数并告知用户（对应 `summarized.json` 中 `todo` 项）。
- [ ] 表格 3–4 张、字数 4500–5500（口径见 README §14；复核清单已自动统计，核对是否在目标区间）。
- [ ] 红线检查：全文无政策预测、无短期煤价评论；评级数据仅列公开可查项，缺失标 `N/A`。
- [ ] 附录含来源清单与待核实区；「下月关注」列出待跟踪事项。

## 7. 交付与人工复核

- 交付物：`report.html`（主稿）、`report.docx`（可选）、`review_checklist.md`、中间 JSON（`raw/ranked/summarized.json`，供审计复跑）。
- 必须明确告知：这是**初稿**，对外发布前由董办 / IR 人工复核确认；本 Skill 是「约束 + 兜底」，**不构成零幻觉保证**（README §10）。
- 涉及未公开重大事项的素材，先脱敏再进入 LLM 请求；不确定是否敏感时向用户确认（README §11）。
- 不要向用户或仓库暴露 `config/.env` 中的任何密钥。

## 8. 异常与降级

| 场景 | 处理 |
|---|---|
| 缺 Key / Key 无效 | 停止（退出码 2 或请求失败），列出缺失项；不生成、不编造 |
| 检索配额耗尽 / 单 query 失败 | 引擎跳过并记入信息缺口，流程继续；交付时汇报缺口条目 |
| LLM 超时 / 输出不合规 | 引擎降级为「待总结（待核实）」并打 `todo`；交付时汇报条数，不得静默 |
| 信息不足（当月动态少） | 依赖补充窗口（§8.1）与缺口单列；建议用户扩关键词或人工补录，不补写无来源内容 |
| 产物缺失或字段不全 | 以 README §12.1 契约核对，指出缺失文件/字段后停止 |

## 9. 禁止事项

- 不在对话中手工替代引擎做检索、打分、渲染（确定性逻辑只在 `scripts/`）。
- 不改动或放宽 README §14 的验收口径。
- 无来源成文、隐藏缺口、把「待核实」改写成确定表述。
- 把密钥写进仓库、提交信息或对话输出。
- 宣称零幻觉、宣称已端到端验证而实际未运行。
