# 1. 技术设计概述

## 1.1 设计目标

股票查询 ChatBI 平台是基于 Python、金融数据接口和 AI Agent 构建的股票智能查询与分析系统。

系统通过自然语言交互实现 A 股股票信息查询、历史行情分析、技术指标计算及交互式数据可视化。

核心技术目标：

1. 构建基于 FastAPI 的统一业务服务层。
2. 使用 Streamlit 构建交互式股票分析前端。
3. 使用 LangGraph 实现 AI Agent 的任务规划与工具调用。
4. 使用 DeepSeek 实现自然语言理解和分析解释。
5. 使用 AKShare 获取中国 A 股行情。
6. 使用 SQLite 缓存历史行情及业务数据。
7. 支持日线、周线、月线和三种复权方式。
8. 使用 Python 实现确定性的技术指标计算。
9. 使用 SSE 提供 AI 分析及任务执行的流式反馈。
10. 保持模块解耦，为后续增加数据源、模型、工具、用户系统及商业化能力提供扩展空间。

## 1.2 技术设计原则

### 1.2.1 业务逻辑与 AI 解耦

AI Agent 不直接操作底层行情接口、数据库或任意代码执行环境。

AI Agent 通过已注册的业务工具调用股票相关能力。

股票信息获取、指标计算和数据校验由 Python 业务服务负责。

### 1.2.2 数据优先于模型生成

股票价格、成交量、技术指标、财务指标等数值应从真实数据获取，或者通过确定性算法计算。

大模型只负责：

- 用户意图识别。
- 任务规划。
- 工具选择。
- 结果组织。
- 数据解释。
- 风险和局限性说明。

### 1.2.3 模块化设计

系统按职责划分为：

- 前端展示层。
- API 接口层。
- 业务服务层。
- Agent 编排层。
- 工具注册层。
- 数据适配层。
- 指标计算层。
- 数据持久化层。
- 后台任务层。

### 1.2.4 优先 MVP

第一阶段优先完成核心业务闭环。

不提前引入复杂的分布式架构、Kubernetes、完整支付平台或企业级微服务体系。

### 1.2.5 保持扩展能力

第一阶段虽然只使用 DeepSeek 和 AKShare，但模型接入、行情适配、工具注册等模块都采用可扩展接口设计。

### 1.2.6 数据可追溯

所有用于 AI 分析的业务数据应具备：

- 股票标识。
- 数据日期。
- 数据来源。
- 复权方式。
- 行情周期。
- 指标参数。
- 计算方法。
- 必要的数据版本信息。

- 对话消息展示。

负责：

- 接口路由。

- 业务服务调用。
- AI 任务创建。
- SSE 事件推送。
- 错误处理。
- 后续身份认证与权限控制。

### LangGraph

负责：

- 对话状态。
- 意图处理。
- 工具选择。
- 多步骤分析流程。
- 工具执行协调。
- 分支和结束条件。
- Agent 任务状态。

### 数据服务层

负责：

- AKShare 数据获取。
- 股票代码规范化。
- 行情缓存。
- 行情校验。
- 复权处理。
- 周线、月线生成。
- 数据来源记录。

### 指标计算层

负责：

- MA。
- EMA。
- MACD。
- RSI。
- KDJ。
- BOLL。
- 后续扩展指标。

技术指标模块不依赖 DeepSeek。

# 4. 核心业务数据模型

## 4.1 股票标识

系统内部需要统一股票代码格式。

建议使用：

```
SH.600519
SZ.000858
BJ.xxxxxx
```

分别表示不同交易所的股票。

这里的 `BJ.xxxxxx` 为格式示意，实际使用真实股票代码。

对外可以接收：

```
600519
SH.600519
贵州茅台
```

股票名称需要先通过搜索服务映射为唯一的内部股票标识。

不能仅依据数字代码长度推断所有交易所，需结合股票基础资料完成规范化。

## 4.2 日期与时区

统一使用：

```
交易市场时区：Asia/Shanghai
交易日期：YYYY-MM-DD
时间戳：ISO 8601，包含时区信息或统一存储 UTC
```

行情交易日期和系统操作时间是不同概念。

例如：

- 行情日期：股票对应交易日。
- 获取时间：系统下载行情的时间。
- 分析时间：Agent 执行分析的时间。

不能混用。

# 5. SQLite 数据库设计

## 5.1 数据库总体方案

第一阶段使用 SQLite。

设计要求：

- 支持股票基础资料。
- 支持历史行情持久化。
- 支持复权数据处理。
- 支持数据覆盖状态记录。
- 支持 Agent 执行记录。
- 支持工具执行日志。
- 支持后续业务表扩展。

推荐启用 WAL 模式，并通过数据库访问层管理事务和写入并发。

## 5.2 核心数据表

MVP 建议使用以下表：

| 表名                 | 作用                       |
| -------------------- | -------------------------- |
| stocks               | 股票基础信息               |
| daily_prices         | 原始日线行情               |
| adjusted_price_cache | 复权行情缓存               |
| adjustment_factors   | 复权因子（数据源可提供时） |
| data_sync_state      | 行情缓存和同步状态         |
| agent_runs           | Agent 任务记录             |
| tool_execution_logs  | 工具执行日志               |

需要注意：

不同数据源提供复权数据的方式可能不同。

有些接口直接提供前复权或后复权价格，而不提供完整的独立复权因子。

因此，应允许采用经过验证的调整价格序列作为数据来源，不能假设 AKShare 所有行情接口都提供独立复权因子。

## 5.3 stocks 表

用于保存股票基础信息。

```
CREATE TABLE stocks (
    symbol TEXT PRIMARY KEY,
    stock_code TEXT NOT NULL,
    stock_name TEXT NOT NULL,
    exchange TEXT NOT NULL,
    industry TEXT,
    listing_date TEXT,
    listing_status TEXT,
    source TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE INDEX idx_stocks_name
ON stocks(stock_name);

CREATE INDEX idx_stocks_code
ON stocks(stock_code);
```

字段说明：

| 字段           | 说明             |
| -------------- | ---------------- |
| symbol         | 内部统一股票标识 |
| stock_code     | 原始股票代码     |
| stock_name     | 股票名称         |
| exchange       | 交易所           |
| industry       | 行业分类         |
| listing_date   | 上市日期         |
| listing_status | 上市状态         |
| source         | 数据来源         |
| updated_at     | 更新时间         |

部分基础信息字段允许为空，表示数据源没有提供相应内容。

## 5.4 daily_prices 表

保存不复权日线行情。

```
CREATE TABLE daily_prices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    trade_date TEXT NOT NULL,

    open REAL NOT NULL,
    high REAL NOT NULL,
    low REAL NOT NULL,
    close REAL NOT NULL,

    volume REAL,
    amount REAL,

    source TEXT NOT NULL,
    fetched_at TEXT NOT NULL,

    UNIQUE(symbol, trade_date),

    FOREIGN KEY(symbol)
        REFERENCES stocks(symbol)
);

CREATE INDEX idx_daily_prices_symbol_date
ON daily_prices(symbol, trade_date);
```

建议统一价格、成交量和成交额的单位。

例如：

```
价格：人民币元
成交量：股
成交额：人民币元
```

如果上游返回其他单位，应在适配层转换，并记录原始字段单位和转换规则。

## 5.5 adjusted_price_cache 表

用于保存已经获得或计算的复权行情。

```
CREATE TABLE adjusted_price_cache (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    trade_date TEXT NOT NULL,

    adjust_type TEXT NOT NULL,
    version_id TEXT NOT NULL,

    open REAL NOT NULL,
    high REAL NOT NULL,
    low REAL NOT NULL,
    close REAL NOT NULL,

    source TEXT NOT NULL,
    calculated_at TEXT NOT NULL,

    UNIQUE(
        symbol,
        trade_date,
        adjust_type,
        version_id
    )
);

CREATE INDEX idx_adjusted_cache_lookup
ON adjusted_price_cache(
    symbol,
    adjust_type,
    version_id,
    trade_date
);
```

复权类型：

```
none
qfq
hfq
```

实际实现中，不复权行情可直接使用 `daily_prices`，无需在该表重复存储。

`version_id` 用于区分复权数据批次或依据的公司行为、复权因子版本。

这十分重要，因为前复权历史价格可能因新的除权除息事件发生变化。

## 5.6 adjustment_factors 表

该表属于条件性设计。

只有在所选数据源能够提供可靠复权因子，或系统建立独立复权计算链路时才启用。

```
CREATE TABLE adjustment_factors (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    trade_date TEXT NOT NULL,
    factor REAL NOT NULL,
    factor_type TEXT NOT NULL,
    source TEXT NOT NULL,
    version_id TEXT NOT NULL,
    fetched_at TEXT NOT NULL,

    UNIQUE(
        symbol,
        trade_date,
        factor_type,
        version_id
    )
);
```

不应在复权因子缺失时自行推断一个无法验证的因子并写入正式数据。

## 5.7 data_sync_state 表

记录数据同步或缓存覆盖信息。

```
CREATE TABLE data_sync_state (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    symbol TEXT NOT NULL,
    dataset TEXT NOT NULL,

    start_date TEXT,
    end_date TEXT,

    status TEXT NOT NULL,
    source TEXT,
    last_success_at TEXT,
    last_attempt_at TEXT,
    error_message TEXT,

    UNIQUE(symbol, dataset)
);
```

该表用于保存总体同步状态。

需要特别注意，`start_date` 和 `end_date` 不能单独证明区间内每个交易日的数据都齐全。

数据完整性仍需结合交易日历、停牌状态和实际行情记录进行检查。

## 5.8 agent_runs 表

保存 AI Agent 任务记录。

```
CREATE TABLE agent_runs (
    run_id TEXT PRIMARY KEY,

    question TEXT NOT NULL,
    status TEXT NOT NULL,

    started_at TEXT NOT NULL,
    finished_at TEXT,

    model_provider TEXT,
    model_name TEXT,

    input_tokens INTEGER,
    output_tokens INTEGER,

    error_code TEXT,
    error_message TEXT
);
```

任务状态建议采用：

```
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED
TIMED_OUT
```

MVP 可以只实现运行中、完成和失败所需的最小状态管理；完整任务恢复能力在后续阶段增强。

## 5.9 tool_execution_logs 表

记录工具执行信息。

```
CREATE TABLE tool_execution_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    run_id TEXT NOT NULL,
    tool_name TEXT NOT NULL,

    input_summary TEXT,
    result_summary TEXT,

    status TEXT NOT NULL,

    started_at TEXT NOT NULL,
    finished_at TEXT,

    duration_ms INTEGER,
    error_code TEXT,
```

## 6.1 设计目标

## 6.2 数据源接口

4. 将成交量和成交额转换为统一单位。

# 7. 行情缓存与更新设计

## 7.1 已确认策略

采用：

**按需获取 + SQLite 缓存 + 查询时检查并补齐。**

完整版本再增加全市场交易日自动同步。

## 7.2 缓存查询流程

```
flowchart TD
    A[用户请求行情] --> B[检查股票和日期参数]
    B --> C[查询 SQLite 缓存]
    C --> D{数据是否覆盖要求?}

    D -->|是| E[读取缓存]
    D -->|否| F[调用 AKShare]

    F --> G[解析并标准化数据]
    G --> H[执行数据校验]
    H --> I{是否有效?}

    I -->|是| J[写入 SQLite]
    I -->|否| K[记录异常]

    J --> E
    E --> L[生成指定周期和复权数据]
    L --> M[返回行情及来源信息]

    K --> N[返回错误或有效部分数据]
```

## 7.3 缓存唯一性

对于原始日线数据：

```
symbol + trade_date
```

作为逻辑唯一键。

写入时采用幂等方式，避免重复记录。

## 7.4 数据补齐

补齐不能仅根据自然日是否连续判断。

建议结合：

- A 股交易日历。
- 股票上市时间。
- 停牌状态。
- 查询区间。
- 数据源覆盖情况。

对于尚不能确定是否缺失的数据，应保留未知状态，而不是直接生成虚构行情。

## 7.5 缓存更新策略

建议区分：

### 历史稳定区间

可较长时间使用缓存。

### 近期交易日

查询时检查数据是否已更新到最近有效交易日。

### 存在公司行为的区间

必要时刷新对应复权数据。

### 数据质量异常区间

重新从数据源获取，校验通过后再更新缓存。

## 7.6 并发处理

当多个请求同时查询同一股票的缺失区间时，应避免重复下载和写入。

MVP 可使用：

- 进程内按股票协调。
- SQLite 唯一约束。
- 幂等写入。
- 有限重试。
- 短事务。

但进程内锁不能跨多个独立进程提供完整互斥。

后续调度器与 Worker 并发运行时，还需要数据库状态协调或适当的任务去重机制。

## 7.7 SQLite 配置

建议：

```
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
```

`journal_mode` 可以在数据库初始化时设置。

`foreign_keys` 和 `busy_timeout` 等连接级配置应对实际数据库连接正确应用。

WAL 能改善读写并发，但不意味着 SQLite 支持无限并行写入。

# 8. 周线与月线生成设计

## 8.1 周线聚合

根据有效交易周内的日线记录生成：

- 开盘价：本周首个有效交易日的开盘价。
- 最高价：本周最高价。
- 最低价：本周最低价。
- 收盘价：本周最后一个有效交易日的收盘价。
- 成交量：本周成交量合计。
- 成交额：本周成交额合计。

## 8.2 月线聚合

根据有效交易月内的日线记录生成：

- 开盘价：本月首个有效交易日的开盘价。
- 最高价：本月最高价。
- 最低价：本月最低价。
- 收盘价：本月最后一个有效交易日的收盘价。
- 成交量：本月成交量合计。
- 成交额：本月成交额合计。

## 8.3 聚合规则

1. 只使用有效交易数据。
2. 不补造休市日价格。
3. 不将停牌误认为无效交易。
4. 应明确当前周或月是否已经结束。
5. 复权价格的聚合应基于相同版本和口径的日线序列。
6. 成交量和成交额不因价格复权而被任意改变。
7. 应记录周期聚合方法和对应交易日期区间。

# 9. 复权数据设计

## 9.1 支持的复权方式

| 类型   | 标识 |
| ------ | ---- |
| 不复权 | none |
| 前复权 | qfq  |
| 后复权 | hfq  |

默认：`qfq`。

## 9.2 数据处理策略

建议优先保存原始日线行情。

前复权、后复权可以通过经过验证的复权因子计算，也可以使用数据源直接提供的调整后价格序列。

关键要求：

**必须记录复权来源及版本，不允许把不同复权口径的数据混用。**

## 9.3 复权切换流程

```
用户切换复权方式
         ↓
确定目标股票和日期区间
         ↓
获取对应复权行情
         ↓
检查数据来源和版本
         ↓
生成日周月 K 线
         ↓
重新计算技术指标
         ↓
更新图表及 AI 分析上下文
```

## 9.4 复权缓存失效

当发生新的除权除息事件或复权数据源修订时，历史调整价格可能变化。

因此需要：

- 识别复权数据版本。
- 保留获取或计算时间。
- 能够重新生成调整价格。
- 避免过期复权缓存长期作为最新结果。
- 必要时刷新受影响的指标和图表。

# 10. 技术指标计算模块

## 10.1 设计目标

技术指标由独立 Python 模块实现。

指标模块接受标准行情数据，返回标准化指标结果。

不依赖 AI 模型。

## 10.2 指标接口

建议定义：

```
class IndicatorCalculator:

    def calculate(
        self,
        prices,
        indicator_name: str,
        params: dict,
    ):
        ...
```

实际实现应进一步指定：

- 输入数据类型。
- 所需字段。
- 输出结构。
- 参数校验规则。
- 样本不足行为。
- 指标计算口径。

## 10.3 指标注册机制

示例：

```
INDICATOR_REGISTRY = {
    "MA": calculate_ma,
    "EMA": calculate_ema,
    "MACD": calculate_macd,
    "RSI": calculate_rsi,
    "KDJ": calculate_kdj,
    "BOLL": calculate_boll,
}
```

支持通过指标名称选择计算实现。

## 10.4 MA

公式：

```
MA(N) = 最近 N 个有效收盘价的算术平均值
```

常用参数：

```
5
10
20
60
```

## 10.5 EMA

常见计算形式：

```
alpha = 2 / (N + 1)

EMA_t = alpha × Close_t
        + (1 - alpha) × EMA_(t-1)
```

EMA 的初始化方式必须统一。

## 10.6 MACD

建议使用：

```
EMA12
EMA26

DIF = EMA12 - EMA26

DEA = DIF 的 9 周期 EMA

MACD_HIST = 2 × (DIF - DEA)
```

不同平台可能采用不同柱值倍数定义。

系统需要固定计算标准，并在指标元数据中标注。

## 10.7 RSI

RSI 基于一定周期内的上涨和下跌变化计算。

常见表达为：

```
RS = 平均上涨幅度 / 平均下跌幅度

RSI = 100 - 100 / (1 + RS)
```

平均值可采用不同平滑口径。

系统应明确选择的算法，并使用参考样本进行验证。

对于分母为零等边界情况，应定义明确处理方式。

## 10.8 KDJ

核心依赖 RSV：

```
RSV =
(Close - LowestLow)
/
(HighestHigh - LowestLow)
× 100
```

然后对 RSV 进行 K、D 平滑并计算 J。

具体平滑参数和初始化方式需要统一。

当最高价与最低价相等时，必须处理零分母。

## 10.9 BOLL

常见计算方式：

```
MID = MA(Close, N)

UPPER = MID + K × STD(Close, N)

LOWER = MID - K × STD(Close, N)
```

建议默认：

```
N = 20
K = 2
```

标准差的总体或样本口径应在实现时固定并记录。

## 10.10 计算数据要求

指标计算前，需要：

1. 确认股票代码。
2. 确认分析周期。
3. 确认复权类型。
4. 获取足够的历史样本。
5. 清理非法或重复记录。
6. 按时间升序排序。
7. 执行指标计算。
8. 返回有效区间及缺失说明。

## 10.11 预热数据

例如，用户要求最近 30 个交易日的 MA60。

系统不能仅获取 30 条行情后直接计算完整 MA60。

应先获取足够的历史数据用于指标预热，再裁剪到用户要求的展示区间。

对于 EMA、MACD 等递推型指标，预热区间可能需要比名义周期更长。

## 10.12 指标结果模型

建议返回：

```
{
  "symbol": "SH.600519",
  "period": "daily",
  "adjust": "qfq",
  "indicator": "MA",
  "params": {
    "window": 20
  },
  "method": "SMA",
  "values": [
    {
      "date": "2026-10-20",
      "value": 1450.25
    }
  ],
  "source": "calculated",
  "price_source": "AKShare",
  "method_version": "1.0"
}
```

上述数据是格式示例，不代表真实股票行情。

# 12. SSE 流式通信设计

## 12.1 设计目标

将 AI Agent 执行过程以事件流方式传输给 Streamlit 前端。

支持：

- 任务开始。
- 工具调用进度。
- 工具执行结果。
- 分析文本增量。
- 图表准备完成。
- 分析结束。
- 错误状态。

## 12.2 建议通信流程

```
sequenceDiagram
    participant UI as Streamlit
    participant API as FastAPI
    participant AG as LangGraph
    participant TOOL as 业务工具

    UI->>API: POST /agent/chat
    API-->>UI: run_id

    UI->>API: GET /runs/{id}/events

    API-->>UI: task_started
    API->>AG: 启动分析

    AG->>TOOL: 调用行情工具
    API-->>UI: tool_started

    TOOL-->>AG: 行情结果
    API-->>UI: tool_completed

    AG->>TOOL: 调用指标工具
    TOOL-->>AG: 指标结果

    API-->>UI: message_delta
    API-->>UI: chart_ready
    API-->>UI: task_completed
```

以上是逻辑调用顺序，具体事件应由统一任务事件服务发布，而不是让多个组件直接无序写入同一 SSE 响应。

## 12.3 SSE 事件格式

例如：

```
id: 1
event: task_started
data: {"run_id":"example-run-001"}

id: 2
event: tool_started
data: {"tool":"get_kline"}

id: 3
event: tool_completed
data: {"tool":"get_kline","status":"success"}

id: 4
event: message_delta
data: {"text":"根据获取的历史行情，"}

id: 5
event: chart_ready
data: {"chart_id":"chart-001"}

id: 6
event: task_completed
data: {"status":"SUCCEEDED"}
```

SSE 响应应采用：

```
Content-Type: text/event-stream
```

## 12.4 事件设计要求

- 每个任务有唯一 run_id。
- 任务内部事件有可排序的序号。
- 工具完成事件必须对应真实执行结果。
- 终态事件只能表达实际任务状态。
- 连接断开不应自动被解释为任务失败。
- 客户端重连需要能够查询任务最终状态。
- 如果实现事件重放，应保留事件序号或事件日志。

## 12.5 MVP 实现边界

MVP 先实现单机可运行的流式任务处理。

需要避免一种常见问题：

`POST /agent/chat` 返回任务 ID 后，如果没有任何后台执行机制，后续 SSE 连接无法凭空启动或恢复任务。

因此建议使用明确的任务执行协调组件，由 FastAPI 创建任务并安排执行，事件服务读取对应任务事件。

本地单进程可采用受控的异步任务执行方式，但需要考虑进程退出与异常恢复限制。

后续完整任务调度使用独立 Worker。

# 13. LangGraph Agent 架构

## 13.1 设计目标

使用 LangGraph 实现股票分析 Agent。

支持：

- 对话状态管理。
- 动态任务规划。
- 工具选择。
- 多工具执行。
- 条件分支。
- 结构化结果。
- 错误处理。
- 流式事件。

## 13.2 Agent 处理流程

```
flowchart TD
    START([开始]) --> INPUT[读取用户问题与上下文]
    INPUT --> PLAN[DeepSeek 理解与规划]
    PLAN --> DECIDE{是否需要工具?}

    DECIDE -->|需要| VALIDATE[校验工具及参数]
    VALIDATE --> EXEC[执行注册工具]
    EXEC --> CHECK{结果是否有效?}

    CHECK -->|有效| COLLECT[收集结构化证据]
    CHECK -->|失败| ERROR[错误处理]

    COLLECT --> NEXT{是否需要更多工具?}
    NEXT -->|是| PLAN
    NEXT -->|否| RESULT[组织分析结果]

    DECIDE -->|不需要| RESULT
    ERROR --> RESULT

    RESULT --> OUTPUT[流式输出]
    OUTPUT --> END([结束])
```

实际执行时应限制最大模型调用轮数、工具调用次数与总执行时间，防止无限循环。

## 13.3 Agent 状态设计

建议定义：

```
from typing import TypedDict, Any


class AgentState(TypedDict, total=False):
    run_id: str

    user_message: str
    messages: list[Any]

    symbol: str
    period: str
    adjust: str

    analysis_start_date: str
    analysis_end_date: str

    selected_indicators: list[str]

    tool_results: list[dict]
    evidence: list[dict]

    error_code: str | None
    status: str
```

这是最小结构示例。

正式实现时应进一步明确：

- 消息如何合并。
- 工具结果如何追加。
- 哪些字段允许覆盖。
- 错误如何传播。
- 图表参数如何保存。
- 节点是否允许重复执行。

## 13.4 Agent 节点设计

建议包括：

| 节点             | 职责               |
| ---------------- | ------------------ |
| normalize_input  | 规范化用户输入     |
| planner          | 理解问题并选择工具 |
| validate_tool    | 工具名称和参数校验 |
| execute_tool     | 调用工具           |
| collect_evidence | 组织数据证据       |

# 15. AI 分析结果与证据模型

## 15.1 设计目标

Agent 输出应与普通自由文本区分，形成可供前端渲染的结构化业务结果。

## 15.2 建议结果结构

```

  "analysis_context": {
    "period": "daily",
    "adjust": "qfq",
```

## 15.3 事实与推断分离

### facts

只保存可以验证的数据事实或计算结果。

### interpretations

保存基于客观数据形成的分析推断。

### scenarios

保存带前提条件的情景假设。

### limitations

保存数据缺失、样本不足和模型局限。

### evidence

保存关联证据，例如：

```
{
  "type": "indicator",
  "symbol": "SH.600519",
  "name": "MA",
  "params": {
    "window": 20
  },
  "period": "daily",
  "adjust": "qfq",
  "source": "calculated",
  "price_source": "AKShare",
  "data_date": "2026-10-20"
}
```

## 15.4 数据可信度原则

不采用未经验证的模型主观可信度百分比。

如果证据不足，应明确输出：

```
数据不足，无法支持确定性分析结论。
```

风险提示不能替代正式商业上线时所需的法律及合规审查。

# 17. 后台任务调度设计

## 17.1 设计目标

后续完整版本需要支持：

- 全市场日线同步。
- 数据缺失补齐。
- 行情校验。
- 定时更新。
- 失败重试。
- 任务状态查询。
- 任务取消及恢复。

## 17.2 已确认技术架构

使用：

```
APScheduler
    ↓
任务持久化或任务创建
    ↓
独立 Worker
    ↓
业务服务
    ↓
SQLite
```

## 17.3 调度器职责

APScheduler 负责：

- 判断需要执行的任务。
- 按指定时间触发。
- 创建业务任务。
- 避免不必要的重复调度。

不建议在调度器进程内部执行大量阻塞性的全市场行情下载。

## 17.4 Worker 职责

Worker 负责：

- 领取或接受任务。
- 调用业务服务。
- 更新任务状态。
- 记录执行结果。
- 处理异常。
- 按规则重试。

## 17.5 任务状态机

```
PENDING
   ↓
RUNNING
   ├── SUCCEEDED
   ├── FAILED
   ├── TIMED_OUT
   └── CANCELLED
```

## 17.6 SQLite 并发约束

SQLite 适合初期开发，但不适合无限制的高并发写入。

建议：

- 单独协调任务写入。
- 启用 WAL。
- 控制 Worker 数量。
- 使用短事务。
- 避免长时间持有写锁。
- 任务创建使用幂等标识。
- 异常恢复时判断任务是否已经执行。

后续可迁移：

```
SQLite → PostgreSQL

简单任务协调 → Redis / Celery 等队列方案
```

迁移属于扩展路线，不属于第一阶段必须交付内容。

# 28. 技术风险与应对方案

| 风险                        | 影响                 | 应对方案                     |
| --------------------------- | -------------------- | ---------------------------- |
| AKShare 接口变化            | 数据获取失败         | 独立适配器、数据校验、测试   |
| DeepSeek 接口或模型能力变化 | 工具调用失败         | 模型适配层、兼容性测试       |
| SQLite 并发写入限制         | 数据库锁冲突         | WAL、短事务、写入协调        |
| 复权历史数据变化            | 指标与历史结果不一致 | 复权版本和缓存刷新           |
| 交易日历不准确              | 缓存误判缺失         | 交易日历及状态校验           |
| 指标算法口径差异            | 与其他平台结果不同   | 明确公式、参数和参考测试     |
| Agent 工具循环              | 成本增加、任务超时   | 工具和模型调用次数限制       |
| SSE 连接中断                | 前端看不到最终结果   | 任务状态查询、必要的事件恢复 |
| 模型生成错误                | 误导用户             | 结构化证据、禁止编造数值     |
| 外部数据商业授权            | 上线受限             | 正式上线前核实授权           |
| 商业化金融合规              | 功能上线受限         | 上线前完成适用合规审查       |

# 29. 安全设计

## 29.1 API 安全

- 请求参数校验。
- 合理的请求大小限制。
- 外部调用超时。
- 访问频率限制。
- 业务错误与内部异常分离。
- 必要的 CORS 限制。
- 后续用户权限校验。

## 29.2 Agent 安全

- 只允许调用注册工具。
- 工具参数进行服务端校验。
- 不执行任意模型生成代码。
- 不执行任意模型生成 SQL。
- 不允许工具访问无关文件。
- 限制工具调用次数和总耗时。
- 将用户输入及数据源文本视为不可信内容。
- 不允许外部数据中的指令改变系统规则。

## 29.3 数据安全

- SQLite 文件权限控制。
- 数据库备份。
- 敏感信息最小化保存。
- 后续用户数据隔离。
- 积分账务审计。
- 管理员操作审计。

## 29.4 开发与生产隔离

- 开发环境使用独立配置。
- 不在仓库保存真实密钥。
- 不将测试密钥与生产密钥混用。
- 生产日志避免暴露个人或敏感信息。
- 对需要商业许可的数据源按实际授权范围使用。

```
    ↓

                    ↓

          ↓

          ↓
```

```
          ↓

          ↓
Python 计算技术指标
          ↓
汇总结构化数据证据
          ↓
DeepSeek 解释结果
          ↓
通过 SSE 返回执行过程
          ↓
Streamlit 展示分析卡片与交互图表
```
